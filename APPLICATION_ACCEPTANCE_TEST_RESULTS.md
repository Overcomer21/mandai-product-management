### Referential integrity and test-product cleanup

The tester confirmed through read-only SQL that products **#2121, #2122 and #2124** are active, have stock **1** each, and each have **one** `OrderItems` reference. Cleanup DELETE attempts returned **HTTP 409**. Inspection of `src/infrastructure/catalog-repository.js` showed that `DELETE FROM Products WHERE Id=@p0` translates SQL Server foreign-key error **547** into **HTTP 409**. Preserving referenced products and their order history is the agreed business requirement.

The test runner uses the term *deactivation* in its cleanup messages, but the observed repository implementation uses **physical DELETE**, **not soft-delete**. Therefore HTTP 409 on transaction-linked products is **expected referential-integrity protection**, not a failed business function. The product **#2120** cleanup returned **404** because the earlier CRUD lifecycle had already deleted it; the script did not independently verify the reason for that 404. No SQL cleanup, hard-delete or reactivation is recommended for retained order-linked products.

**Inactive product rule:** Products with `IsActive = 0` must not be used for new customer purchases or subsequent purchase/concurrency test inputs. Public catalog reads already filter to `IsActive=1` in the inspected Node.js repository.

Separate K6 TCP failures were excluded from the comparative Python benchmark and remain a distinct reliability consideration.
