# Mandai Product Management — Node.js migration candidate (PARTIAL)

**This is a migration candidate, not a production cutover build. Do not replace FastAPI with it yet.**

## Evidence and scope

Audited the supplied `BackendApp.zip`, `tests2.zip`, `sql.zip`, `scripts.zip`, `scritps.zip`, `start-backend.zip`, and Flutter `Lib (2)(1).zip` on 2026-11-04. Sources were inspected read-only. No original files, remote repositories, or SQL databases were changed. No application secrets were copied into this archive.

### Migrated code

- HTTP entrypoint with independent SERVICE_MODE `all | catalog | identity | commerce | admin` for independently hosted service processes.
- Reusable catalog admin/customer SQL Server repository, category/count/pagination/filter/sort/detail, create/update/delete, stock stats.
- Domain/app/repository/interface layering with explicit dependency injection of application services.
- JWT HS256 authorization (4 hours), Argon2 password verification, admin/customer permissions.
- Purchase and demo cart checkout with SQL Server transactions, uniqueness constraint reliance, sorted multi-product stock deductions, compare-and-update stock, rollback, and Python-compatible idempotency request fingerprints.
- Customer account and order history/details response shapes.
- Redis optional caching for customer catalog and invalidation after the migrated purchase/demo checkout/admin CRUD paths. Redis-backed login guard is *opt in* and does not yet demonstrate parity with all Python `login_guard` combinations.
- Initial Kafka producer adapter is included, **not wired**: publishing must only be driven from a durable outbox and must not be moved into stock/payment SQL transactions.
- NGINX multi-instance routing and example Compose topology. No backing SQL Server/Redis/Kafka is auto-provisioned or modified.

### Missing / NOT migrated

- `/api/stripe-checkout/sessions`, `/api/stripe-checkout/orders/:id`, `.../:id/cancel`, `.../:id/reconcile`, `.../:id/resume`, Stripe webhook and `/api/payment-return/:outcome`, plus `/api/stripe-checkout/return/session/:sessionId`.
- Stripe sandbox standalone test router, settlement, reconciliation, fast-expiry worker, recovery and complete payment outbox dispatcher.
- `/api/admin/testing/report`, `/api/admin/testing/run-all`, `/api/admin/testing/run-all/status`, `/api/admin/concurrency-tests` and media static file serving.
- Exact login guard behavior/retry-after and shared counter keys must be cross-checked against Python implementation. Example guard uses SHA-256(email|IP) and a 5-failure threshold for 900 seconds.
- Existing Python test suites have not been ported or passed against SQL Server.
- No integration test or benchmarks against MandaiDB, Stripe, Redis, Kafka, Docker, load balancing or Flutter were executed. No end-to-end payment proof.
- No SQL Server migration/schema modification is included. Existing tables and constraint names are assumed from the supplied SQLAlchemy models and must be checked before database connection.

### Run local checks (do not connect to production DB)

```
node --version
npm install
npm test
npm run check
```

The seven `node --test` checks use fake repositories and do not need database connections. The Jest-like output is generated by Node's built-in test runner.

### Local server (only after configuring a disposable SQL Server)

```
cp .env.example .env
# configure the .env locally; do not commit it
npm start
```

`SERVICE_MODE=all` serves the implemented endpoints on port 8000. Docker deployment `deploy/docker-compose.yml` illustrates isolated processes behind NGINX but **is not a ready-to-deploy production stack**. Before deploying Compose, update DB_HOST to a host reachable from Docker and supply TLS certificate validation.

**Do not run node and original Python application against the same live checkout environment during verification without an isolation plan.** Shared idempotency keys and stock apply across both.

### Architecture

```
Flutter (unchanged)
  -> NGINX (example port 51871)
       -> Catalog API replicas -> CatalogService -> Catalog repository -> existing SQL Server
                         \-> Redis optional cache
       -> Identity API -> IdentityService -> Identity repository -> existing SQL Server
       -> Admin API -> CatalogService -> Catalog repository -> existing SQL Server
       -> Commerce API replicas -> OrderService -> Order repository -> existing SQL Server
                                                   \-> catalog cache generation invalidation
Future: durable SQL outbox -> dispatcher -> Kafka -> idempotent consumers
```

This is **logical service separation**, with a single existing shared database preserved per the requested non-destructive migration. Independent deployability and ownership boundaries remain limited by shared schema. Kafka adapter is a placeholder until durable outbox integration is completed.

### Additional correctness / production parity checks required

1. Compare FastAPI OpenAPI route/method/status/response schemas with Node.js output for every consumed Flutter API.
2. Ensure `ProductInput` Pydantic validation/error structure and optional/default semantics are equivalent where the client depends on them.
3. Validate SQL Server query plans, case-insensitive search, wildcard escaping, decimal exactness, default sorting and pagination.
4. Validate existing JWT interoperability in both directions, including expiry, subject and password-hash algorithm. Validate Redis throttling and 429 headers.
5. Execute both original and migration candidates against **isolated disposable test databases** and compare results for failed/duplicate/concurrent purchases, payment declines, inventory unchanged after rollback.
6. Implement Stripe exactly using webhook signature verification, durable payment state transitions, expiry/cancel/reconcile/resume, events, and outbox; never mark orders paid from browser return.
7. Invalidate or refresh catalog caches after every inventory mutation including Stripe reserve/cancel/refund. Cache generation may race between processes and provider outages require a defined fallback.
8. Compare Docker/NGINX stress results under like-for-like user/request parameters (e.g. 100, 400, 700), not historical benchmarks from another stack.
9. Add media serving with secure file-root mapping and CORS parity, and recreate Run All Tests behavior without deleting previous FastAPI tests.
10. Plan cutover with rollback, security testing, observability, database pool limits, secret injection and dependency vulnerability scanning.

### Security

Never copy Stripe signing secrets, API keys or database passwords into test fixtures, archives, source code or logs. Application does not log SQL query parameters. `.env` is gitignored and only `.env.example` is included.
